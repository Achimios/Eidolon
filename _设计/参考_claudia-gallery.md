## 可以搬过来的方法
| 他们怎么做 | 我们已有 / 缺口 |
|---|---|
| 先分轨（htdemucs）→ 局部速度（20 s 窗口）→ 每拍吸附鼓起音；小节首拍两票（踢鼓 + 和声变化） | 有 `separate.py` + beat_this；和声票没有 |
| ⭐**词级时间戳**：wav2vec2 强制对齐 + Whisper 兜底，低置信的词交给人听 | ❌缺。我们只有 voice.phrases（乐句级）。要装 whisperX 一类 → 先问 👤 |
| ⭐**歌词跟人声，运动跟拍子**：字按词时间出现、不吸附拍；入场动画 ≤ 1/8 拍 | 跟 pdoom 的「先锚乐句再吸附拍」不矛盾，是更细一层 |
| **每帧 = 歌曲时间的纯函数**（无状态、无随机数、用索引哈希、不读时钟）→ 可并行、乱序、续跑 | 我们大多数工具是这样，但没当成规矩 |
| 无头 Chromium 逐帧截图，1080p 24 fps；画布强制软件后端，每场景重置上下文；单帧限时 | pdoom 类 JS 管线可直接用 |
| 续跑：跳过已有帧，先写临时文件再改名；每 200 帧重开页面 | —— |
| **历史无关性检查**：同一帧在干净页面和「刚渲染过别的帧」的页面各渲一次，像素差 > 40 级算失败 | 可以加进 tests |
| ⭐**歌词门控**：每个演唱词在其时间点渲一帧，确认字真的在屏幕上（按时间匹配） | 依赖词级时间戳 |
| 闪烁检查：96×54 亮度图，每秒明暗对 > 3 算失败（只查闪烁，不替代审片） | 可以加进 `sense_expect` 的审计 |
| ⭐**构建和审核分开**：审核者自己重渲，不看构建者的输出；评分只是参考，机器判过不过；每章最多两轮修改，修完查「每条意见做没做」而不是重新打分 | 我们靠 👤 看样片 |
| 分镜：3 位导演视角 + 3 位评委 + 1 位总导演 | 多视角写分镜可以借鉴 |
| 防 slop：提示词和分镜用固定模板，代理只填空；复杂画面用一条规则迭代生成而不是堆对象；出问题先停、修提示词源头再重做，不从坏图里挑 | 跟哲学 §15「有审美的信息量」一致 |
| 角色一致性靠**文字规范**（发型 / 标志色 / 服装 / 年龄写进每条 prompt），只保留一个强调色 | 我们用参考图（Seedream 支持）；文字规范可以两者都上 |
| 状态文件：DECISIONS.md（导演原话 + 日期，新的覆盖旧的）、ledger.jsonl（每次付费一行）、STATUS.md；导演批准绑定分镜文件的哈希，文件一改批准就失效 | 有 👤 标记和 where_continue；**付费账本没有** |

## 我的判断
- 他们是工业流程（215 小时、预算两千美元起），我们是导演工作室。值得抄的是**验证**，不是规模：词级歌词门控、历史无关性检查、付费账本、审核者独立重渲。
- 跟我们的分歧：他们的分镜由评委打分来收敛，我们由 Thymos 和情绪流来收敛（数学只是积木和审计，见哲学 §15）。
